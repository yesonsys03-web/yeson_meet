# PDF 스토리보드 번역 — 3단(다열) 템플릿 + 세로형 지원 — 설계

- 날짜: 2026-07-31
- 대상 기능: 스토리보드 프로파일의 **추출**(어느 블록을 번역 대상으로 잡는가)
- 상태: 구현 완료 · 실물 검증 완료
- 기준 문서: `FL102_FNL_A_3_PANEL.pdf`(79p) / `FL102_FNL_A_1_PANEL.pdf`(233p)
  및 각각의 사람 납품본 `..._번역.pdf`

## 1. 증상

사용자 신고: "3단 스토리보드 형식은 번역이 안 된다."

실측 결과 **서로 다른 원인 두 개**였다.

| 변형 | 페이지 | 증상 | 원인 |
|---|---|---|---|
| `3_PANEL` (1008×612 가로) | 79 | 1열만 번역, 2·3열 전무 | 프로파일이 "페이지당 필드 1세트" 전제 |
| `1_PANEL` (612×792 **세로**) | 233 | 작업 자체가 "지원하지 않는 PDF 포맷입니다"로 실패 | `detect()`의 가로형 게이트 |

## 2. 원인 1 — 페이지당 필드 1세트 전제 (3단)

`profiles/storyboard.py`는 도입 당시 GABE01(페이지당 판넬 1장)만 보고 만들어졌고,
파일 첫 docstring이 그 전제를 명시하고 있었다("페이지당 판넬 1장").

- `_field_content()`가 라벨을 찾는 즉시 `break` — 페이지의 **첫** `Dialog`만 앵커
- `extract()`가 `_FIELDS`를 페이지당 **한 번만** 순회
- 이어서 후보 필터 `abs(b.bbox[0] - lx0) < 60.0`이 x가 315.4pt 떨어진 2·3열
  내용을 정확히 걸러낸다 — **1열 앵커 기준으로는 올바른 동작**이라 오류 없이
  조용히 누락된다

`_next_label_y0`의 docstring은 이 실패를 문자 그대로 예고해 뒀었다:
*"장차 라벨이 여러 열에 걸친 템플릿을 만나면 엉뚱한 열의 라벨을 상한으로 잘못
고를 수 있다."*

### 2.1 계량 (FL102_FNL_A_3_PANEL, 79페이지)

| 항목 | 수정 전 | 수정 후 |
|---|---|---|
| 라벨 x0 분포(=열) | 39.0 / 354.4 / 669.8 (156·154·154회) | 동일 |
| `extract()` 블록 | 48 | **127** |
| 블록의 열별 분포 | **`{39.0: 48}`** (100% 1열) | `{39.0: 48, 354.4: 40, 669.8: 39}` |
| 그중 알파벳 없는 것(`1/2` 등) | 23 | 67 |
| 실질 번역 대상 | 25 | **60** |
| 사람 납품본의 필드 한글 주석 | 59 (1열 25 / 2열 18 / 3열 16) | — |
| 사람 주석 중 우리가 못 뽑은 것 | 34 (2·3열 전부) | **0** |

수정 전 "1열 실질 25건"이 사람의 "1열 25건"과 **정확히 일치**한다 — 1열은
원래도 완벽히 처리됐고 나머지 두 열이 파이프라인에 진입조차 못 했다는 뜻이다.

교차 검증: 같은 에피소드의 `1_PANEL`(233p) 익스포트도 수정 후 **127블록**으로
3단과 정확히 같은 수가 나온다(같은 내용의 다른 레이아웃이므로 일치해야 맞다).

## 3. 원인 2 — 가로형 게이트 (세로형)

`detect()`가 `w <= h`면 즉시 `False`였다. FL102의 `1_PANEL` 익스포트는
**612×792 세로형**이라 `detect_profile()`이 `None`을 돌려주고
`pdf_run.py`가 `PdfTranslateError("지원하지 않는 PDF 포맷입니다")`로 잡을 죽인다.

이 게이트는 애초에 **판별력도 없었다**: 타당성 문서가 조사한 4개 포맷
(스토리보드 1008×612 / 대본 / 컬러노트 792×612 / 리드시트 792×612)이 전부
가로형이라, 가로·세로는 스토리보드를 다른 포맷과 구분해주지 않는다. 실제
판별자는 `Dialog` + `Action Notes` 라벨 2종의 존재다.

## 4. 결정

1. **앵커를 열거한다.** `_field_anchors(raws, label)`가 페이지 안의 라벨 앵커를
   전부 돌려주고, `extract()`가 앵커마다 독립적으로 자기 열을 처리한다.
   1단은 앵커 1개라 기존과 동일한 경로다.
2. **`_field_content`는 앵커를 인자로 받는다.** 스스로 찾아 `break`하지 않는다.
   열 판정(`abs(x0 - 앵커 x0) < _COL_TOL`)은 그대로 — 열 간격 315.4pt ≫ 60pt라
   열끼리 섞이지 않는다.
3. **다음 라벨은 같은 열 우선, 없으면 페이지 전역 폴백.** 열 제한만 두면 라벨
   x가 열 허용폭 밖으로 흔들리는 템플릿에서 Dialog의 창이 아래로 열려
   **다음 필드 내용을 삼키는** 기존 안전성질(빈 Dialog Bug A/B)을 잃는다.
   실물 3단은 열마다 두 라벨이 다 있어 폴백이 발동하지 않는다.
4. **내용 창의 하한에 필드 박스 하단을 결합한다.** 마지막 필드(Action Notes)는
   뒤에 라벨이 없어 창이 페이지 끝까지 열려 있었다 — §5 참조.
5. **우측 폴백의 오른쪽 끝을 `limit_x1`로 조인다.** — §6 참조.
6. **`detect()`의 가로형 게이트를 제거한다.** 판정 근거는 라벨 2종뿐.
7. **필드 박스 문턱(`_FIELD_BOX_MIN_WIDTH=300`)은 손대지 않는다.** 3단 박스
   실측이 306.4pt로 통과하기 때문이다 — 다만 여유가 **6.4pt뿐**이라 4단 등
   더 좁은 열을 만나면 조용히 박스를 놓친다(§8 잔여 위험).

## 5. 근거 — 마지막 필드 창을 박스 하단으로 막는 이유

3단 문서의 페이지 푸터(`FL102_FNL_A Property of Netflix & Robin Red Breast`,
x0=405.8)는 **2열 x0(354.4)과 51.4pt 차이**라 x 허용폭 60pt 안에 들어온다.
마지막 필드는 창 상한이 없으므로 푸터가 2열 Action Notes 내용으로 빨려 들어간다.

| 문서 | 박스 하단으로 조일 때 잃는 블록 |
|---|---|
| GABE01_A1 (1단, 표본 149p, Action Notes 148건) | **0건** — 기존 코퍼스에 무해 |
| FL102 3단 (79p 전수) | **77건 — 전부 페이지 푸터**(=제거해야 할 오염) |

즉 이 상한은 기존 동작에 no-op이고 3단에서만 실제 버그를 잡는다.

박스 조회 기준도 "병합 내용 bbox"에서 **"라벨 앵커 bbox"**로 바꿨다(창을
계산하려면 내용을 모으기 전에 박스가 필요하다). GABE01 표본 206건 전수 대조
결과 **206/206 동일**이라 회귀가 아니다.

## 6. 근거 — 우측 폴백을 열 안으로 조이는 이유

아래 자리가 없어 우측 경로로 떨어진 블록의 오른쪽 끝이 `page_w - 8`이었다.
3단에서는 그게 곧 **옆 열 침범**이다.

실물 FL102 p36 2열 대사(원문 bbox가 박스를 거의 꽉 채워 아래 여유 1.7pt):

| | rect | 비고 |
|---|---|---|
| 수정 전 | `(423.6, 294.3, **1000.0**, 316.8)` 12pt | 열 우측 657.8을 넘어 3열까지 가로지름 |
| 사람 납품본 | `(408.8, 403.4, **535.8**, 416.4)` | 열 안 |
| 수정 후 | 열 우측(657.8 − 8) 이내 | 침범 0건 |

설계 `2026-07-31-...-below-placement-design.md` §6.5는 "우측도 같이 조이면
남은 38%에서 클리핑이 늘어난다"며 이연했으나, **실측에서 재현되지 않았다**:
GABE01 표본 80페이지의 우측 경로 27건에서 **폰트 변화 0건 · 새 클리핑 0건**이고,
오히려 그 **27건 전부가 지금 박스 우측(985.1)을 넘어 1000.0까지** 뻗고 있었다.
조이는 쪽이 순수 이득이다.

## 9. 잔여 위험 / 이번 범위 밖

- **`_FIELD_BOX_MIN_WIDTH = 300.0`의 여유가 6.4pt뿐**(3단 박스 306.4pt). 4단
  이상이나 더 좁은 열 템플릿을 만나면 박스를 못 찾아 조용히 `limit_y=None`
  (= 옛 우측 배치)로 떨어진다. 실물 근거가 생기면 문턱을 열 폭 비례로 바꾸거나
  못 찾았을 때 경고 로그를 남기는 방향
- **패널 콜아웃 OCR은 이번 변경 대상이 아니다.** `_panel_region`이 x를 페이지
  전폭으로 잡아 3단에서도 3개 판넬을 모두 훑는다(FL102 p1 실측:
  `(0.0, 95.0, 1008.0, 289.3)`) — 사람 납품본의 패널 콜아웃 29건에 대한
  실제 검출률은 측정하지 않았다
- 사람의 **Dialog 라벨줄 슬롯**(1단 GABE01 관례)은 여전히 보류 상태다. 이번
  실측으로 그 관례가 **1단 전용**임이 확인됐다 — 3단에서 사람은 대사를 원문
  **아래**에 쓴다(p1 2열: 영문 `y1=356.4` 바로 아래 `y0=358.2`)
